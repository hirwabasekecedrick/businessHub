1. Purpose, Scope and How to Read This Document
This document is the build contract for BusinessHub. It translates the design dossier into decisions a development team
can implement without further arbitration: a frozen technology stack, a complete relational schema, an endpoint-by-
endpoint API catalogue, a permission matrix, state machines, and user stories with testable acceptance criteria.
Anything stated here as MUST is a hard requirement and is covered by an acceptance test. SHOULD marks a strong
recommendation that may be traded away with the product owner's written agreement. MAY marks an option left to
the implementing team.


1.1 In Scope for Release 1
 • Nine functional modules: accounts and organisations, CRM, requests and cases, workflow, documents, finance,
   communication, reporting, administration.
 • Three delivery surfaces: a Next.js web application (internal consoles plus client/partner portal), a Flutter mobile
   application, and a documented public REST API.
 • Multi-organisation tenancy with role-based access control, full audit trail and data isolation.
 • Four outbound integration families: payment, messaging (email/SMS/push), e-signature and object storage.

1.2 Out of Scope for Release 1
 • Machine-learning recommendations, predictive scoring and anomaly detection.
 • Public marketplace and product catalogue.
 • Sector-specific connectors beyond the four integration families above.
 • Native desktop clients and offline-first web usage (the mobile app has a bounded offline queue only).

1.3 Definition of Terms
 Term                      Meaning in this document

 Organisation              Any tenant entity: the operating company itself, a client company, or a partner company. The unit
                           of data isolation.

 Membership                The link between a user and an organisation, carrying exactly one role. A user may hold several
                           memberships.

 Case                      The central business object, also called a request or file. Everything (tasks, documents, invoices,
                           messages) hangs off a case.

 Task                      A unit of work inside a case, assigned to one user, with a type, a due date and a status.

 Approval                  A decision attached to a task, recorded with the deciding user, the level, the outcome and a
                           timestamp.

 SLA                       The contractual deadline attached to a case or task, computed from business calendars, and the
                           source of reminders and escalations.

 Actor                     The authenticated principal performing an action; recorded on every audit event. May be a user or
                           a service account.

2.1 Repository Layout
A single monorepo managed with pnpm workspaces and Turborepo. Flutter lives inside the same repository but outside
the pnpm workspace graph.

 businesshub/
 ├── apps/
 │   ├── api/                   NestJS backend (the only writer to PostgreSQL)
 │   ├── web/                   Next.js — consoles + client/partner portal
 │   ├── worker/                BullMQ consumers: notifications, exports, SLA sweeps
 │   └── mobile/                Flutter application (Android + iOS)
 ├── packages/
 │   ├── contracts/             OpenAPI source of truth + generated TS types
 │   ├── permissions/           Permission codes + RBAC matrix, imported by api and web
 │   ├── ui/                    Shared React components and design tokens

 ├── infra/
 │   ├── docker/                Dockerfiles + docker-compose.yml (dev + CI)

 ├── docs/                      ADRs, runbooks, this specification
 └── .github/workflows/         CI pipelines




2.2 Coding Standards
 • TypeScript strict mode is on everywhere; any requires an inline justification comment.
 • ESLint + Prettier run in a pre-commit hook and again in CI; CI fails on any lint error.
 • Commits follow Conventional Commits; the changelog and semantic version are generated from them.
 • Branch naming: feat/<ticket>-<slug>, fix/<ticket>-<slug>. Direct pushes to main are blocked.
 • Every pull request requires one approving review, green CI, and no drop in coverage below the thresholds in
   section 17.
 • Dart code follows flutter_lints with prefer_const and always_declare_return_types enabled.

3.2 Module Boundaries Inside the API
The backend is a modular monolith, not a set of microservices. Each module owns its tables and exposes a service
interface; cross-module access goes through that interface, never through another module's repository. This keeps a
future extraction into separate services cheap without paying distributed-system costs in release 1.

 apps/api/src/
 ├── modules/
 │   ├── identity/          users, sessions, MFA, password reset, service accounts
 │   ├── tenancy/           organisations, memberships, roles, invitations
 │   ├── crm/               client & partner records, contacts, segments, consents
 │   ├── cases/             requests, case types, SLA computation, comments
 │   ├── workflow/          tasks, approvals, escalations, process templates
 │   ├── documents/         upload sessions, versions, classification, e-signature
 │   ├── finance/           quotations, invoices, payments, reconciliation
 │   ├── messaging/         notification templates, channels, preferences, delivery
 │   ├── reporting/         KPI queries, saved views, exports
 │   └── admin/             reference data, settings, integrations, audit read API
 ├── common/                guards, interceptors, filters, pipes, decorators
 ├── infrastructure/        prisma client, redis, s3, mail, sms, payment adapters
 └── main.ts




3.3 Cross-Cutting Request Pipeline
Every inbound request passes through the same ordered chain. Implement it once, in common/, and never bypass it in a
controller.

 #     Stage                Behaviour                                                                 Failure response

 1     Correlation          Assign or propagate X-Request-Id; open an OpenTelemetry span.             —

 2     Rate limiting        Redis sliding window, keyed by IP for anonymous and by user for           429 with Retry-After
                            authenticated calls.

 3     Authentication       Verify the JWT signature, expiry, issuer and audience; load the           401 AUTH_REQUIRED
                            session.

 4     Tenancy resolution   Resolve the active organisation from X-Organization-Id and                403 ORG_FORBIDDEN
                            confirm the caller holds a membership in it.

 5     Authorisation        Evaluate the required permission code against the membership              403 PERMISSION_DENIED
                            role and any record-level rule.

 6     Validation           Validate and coerce the payload with class-validator DTOs; reject         422 VALIDATION_FAILED
                            unknown properties.

 7     Idempotency          For POST/PATCH/DELETE with an Idempotency-Key, replay the                 200 replay, or 409 on key
                            stored response if the key is known.                                      reuse with a different body

 8     Handler              Execute business logic inside a database transaction where more           Mapped error codes
                            than one table is written.

 9     Audit                Emit an audit event for every mutating action, with before and            Never blocks the response;
                            after snapshots.                                                          failures alert

 10    Serialisation        Strip fields the caller is not allowed to see, then shape the             —
                            envelope.

4.3 Getting the Stack Running Locally
 git clone git@github.com:<org>/businesshub.git && cd businesshub
 cp .env.example .env             # dev defaults; no real secrets required
 pnpm install
 docker compose up -d postgres redis minio
 pnpm --filter api prisma migrate deploy
 pnpm --filter api prisma db seed         # roles, case types, demo tenants, users
 pnpm dev                                 # api :3000, web :3001, worker attached

 # mobile, in a second shell
 cd apps/mobile && flutter pub get && flutter run --dart-define=API_URL=http://10.0.2.2:3000



The seed creates one operating company, two client organisations, one partner organisation, and one user per role
with the password Password123!. Seed data MUST never be loaded in staging or production; the seed script aborts
unless NODE_ENV is local or ci.


4.4 Definition of Ready for a Ticket
 • The user story references a section of this document and names the permission code it exercises.
 • Acceptance criteria are written as Given/When/Then and are automatable.
 • API changes are reflected in packages/contracts before implementation starts.
 • Any new table or column has a migration reviewed alongside the code.
 • The ticket states whether an audit event, a notification, or both, are expected.

5. Identity, Tenancy and Access Control

5.1 Authentication
 Concern                 Requirement

 Password storage        Argon2id, memory 64 MiB, iterations 3, parallelism 4, plus a server-side pepper held in the secret
                         manager.

 Password policy         Minimum 12 characters; rejected if present in the breached-password list (k-anonymity check against
                         an offline dataset). No forced periodic rotation.

 Access token            JWT, RS256, 15-minute lifetime. Claims: sub, sid, orgs[], iat, exp, iss, aud. It carries no permission
                         list — permissions are resolved server-side on every call.

 Refresh token           Opaque 256-bit value, hashed in the database, 30-day lifetime, single use with rotation. Reuse of a
                         consumed token revokes the entire token family and raises a security alert.

 MFA                     TOTP (RFC 6238), 30-second step, ±1 window tolerance. Mandatory for Administrator, Super-
                         administrator and Manager. Ten single-use recovery codes are issued at enrolment and shown
                         exactly once.

 Brute-force defence     Five failed attempts within 15 minutes locks the account for 15 minutes and emails the owner.
                         Counters are per account and per source IP.

 Sessions                Listed per user with device, IP, location and last-seen. A user may revoke any of their sessions; an
                         administrator may revoke any session in their organisation.

 Service accounts        Machine clients use the OAuth 2.0 client-credentials grant. Secrets are shown once, are rotatable,
                         and are scoped to a single organisation and a fixed permission set.



5.2 Tenancy Model
Every business row carries an organization_id. Isolation is enforced at two levels, deliberately redundant: the
application always filters by the active organisation, and PostgreSQL row-level security refuses cross-tenant reads even
if application code is wrong.

 -- Applied to every tenant-scoped table
 ALTER TABLE "case" ENABLE ROW LEVEL SECURITY;

 CREATE POLICY case_tenant_isolation ON "case"
   USING (organization_id = current_setting('app.current_org')::uuid);

 -- The API sets the variable at the start of every transaction:
 --   SET LOCAL app.current_org = '<uuid>';
 -- Requests that legitimately span organisations (super-admin reporting)
 -- run as a role that bypasses RLS and are always audited.

5.5 Record-Level Rules
Role permissions are necessary but not sufficient. After the permission check passes, the following record-level
predicates MUST also hold. They are implemented as a reusable CaseAbility / DocumentAbility service, not copied
into controllers.

 Rule                            Statement

 R-01 Tenant                     The record's organization_id equals the active organisation, unless the caller holds
                                 case.read.all (Super-administrator only).

 R-02 Ownership                  A holder of case.read.own sees only cases where they are the owner, the creator, or an assignee
                                 on a task.

 R-03 Client visibility          A Client sees a case only if their organisation is the case's client organisation, and never sees
                                 internal comments or internal-only tasks.

 R-04 Confidentiality            A document classified confidential is readable only by users holding document.classify, plus
                                 the case owner.

 R-05 Segregation of             The user who created an invoice MUST NOT be the user who approves it, and MUST NOT be the
 duties                          user who records its payment, unless the organisation has fewer than three active finance users, in
                                 which case the override is recorded as an audit event.

 R-06 Approval level             A user may only decide approvals at or below their approval level; an approval above the level
                                 requires escalation, never a silent pass.

 R-07 Closed records             A case in CLOSED or ARCHIVED rejects every mutation except case.reopen and audit reads.

 R-08 Impersonation              While impersonating, all write permissions are denied; the session is read-only and every read is
                                 audited with both the real and the effective actor.

6. Data Model




                                     Figure 2 — Core entities and their relationships


6.1 Conventions
 • Primary keys are UUID v7 (time-ordered), generated by the application, never by a sequence.
 • Every table carries created_at, updated_at (both timestamptz), created_by and updated_by.
 • Deletion is logical: deleted_at timestamptz NULL. Physical deletion happens only through the retention job.
 • Money is stored as numeric(14,2) plus an ISO-4217 currency char(3). Never a float.
 • Enumerations are PostgreSQL enum types so that an invalid value cannot be written.
 • Every foreign key is indexed. Every tenant-scoped table has a composite index leading with organization_id.
 • Free-form business payloads use jsonb with a validated shape at the application layer, never text holding JSON.

7. API Design Conventions
One REST API serves the web application, the mobile application and third parties. There is no privileged internal API:
the consoles use exactly the same endpoints and the same authorisation rules as an external integrator would.


7.1 Base Rules
 Concern             Rule

 Base URL            https://api.businesshub.app/v1. The major version is in the path and only changes on a breaking
                     change.

 Transport           HTTPS only, TLS 1.2 minimum. HTTP requests are refused, not redirected.

 Media type          application/json; charset=utf-8. File bytes never transit the API — see the upload flow in 8.6.

 Naming              Plural, kebab-case collection nouns (/case-types). Field names are camelCase in JSON and snake_case in
                     the database; the mapping lives in one serializer layer.

 Dates               ISO 8601 with an explicit offset, always UTC on the wire (2026-08-16T09:14:00Z). The client renders in
                     the user's timezone.

 Money               An object: { "amount": "4850.00", "currency": "EUR" }. The amount is a string to avoid float
                     rounding in JavaScript.

 Tenancy             The X-Organization-Id header is required on every authenticated call. A token with a single
                     membership MAY omit it; the server then resolves the default membership.

 Idempotency         An Idempotency-Key header is REQUIRED on payment creation and invoice issuance, and honoured on
                     every other mutating endpoint. Keys are retained for 24 hours.

 Compression         gzip and brotli are supported on responses over 1 KB.

7.3 Status Codes and Error Codes
 HTTP      Error code                    Meaning and client behaviour

 400       BAD_REQUEST                   Malformed JSON or an unparsable parameter. Do not retry unchanged.

 401       AUTH_REQUIRED                 Missing or expired access token. Refresh once, then sign the user out.

 401       MFA_REQUIRED                  Credentials are valid but a TOTP challenge is outstanding. Present the challenge.

 403       PERMISSION_DENIED             Authenticated but not authorised. Hide the affordance in the UI; do not retry.

 403       ORG_FORBIDDEN                 The active organisation header does not match a membership. Force organisation re-
                                         selection.

 404       NOT_FOUND                     The resource does not exist, or exists in another tenant. Never disclose which.

 409       CONFLICT                      Version conflict, duplicate unique key, or idempotency-key reuse with a different body.

 409       INVALID_TRANSITION            The requested status change is not allowed from the current state. Reload the record.

 422       VALIDATION_FAILED             Well-formed but semantically invalid. details[] maps one-to-one to form fields.

 423       ACCOUNT_LOCKED                Too many failed sign-ins. Show the unlock time.

 429       RATE_LIMITED                  Quota exceeded. Honour Retry-After; back off exponentially with jitter.

 500       INTERNAL_ERROR                Unexpected server fault. Show a generic message and the requestId for support.

 503       SERVICE_UNAVAILABLE           A dependency is down or the system is in maintenance. Retry after the stated delay.



     LEAK PREVENTION Error messages returned to clients MUST NOT contain SQL, stack traces, internal hostnames or
     provider payloads. The requestId is the only handle a user gives to support, and it MUST appear in the logs of every
     service that touched the request.

7.5 Concurrency, Webhooks and Rate Limits
 Mechanism             Specification

 Optimistic locking    Mutating endpoints return an ETag. A PATCH SHOULD send If-Match; a mismatch returns 409
                       CONFLICT with the current representation so the client can merge.

 Outbound webhooks     Signed with HMAC-SHA256 over the raw body plus a timestamp, in X-BH-Signature. At-least-once
                       delivery, retried at 1 m, 5 m, 30 m, 2 h, 12 h. Consumers MUST be idempotent on eventId.

 Inbound webhooks      Payment and e-signature callbacks verify the provider signature before parsing. An unverified body is
                       logged and discarded, never processed.

 Rate limits           Anonymous 30 req/min per IP; authenticated 600 req/min per user; export endpoints 10 req/min;
                       sign-in 10 req/15 min per account. Limits are returned in X-RateLimit-Limit, -Remaining, -Reset.

 Long operations       Anything over 5 seconds (exports, bulk imports, PDF batches) returns 202 with a job id; the client polls
                       GET /v1/jobs/{id} or listens on the notification stream.

8.6 Documents
File bytes never pass through the API process. Upload is a three-step handshake so that a 40 MB contract does not
occupy a Node worker, and so that a failed or abandoned upload leaves no orphan record in a usable state.

 1) POST /v1/documents/upload-sessions
    { "caseId": "...", "filename": "contract_v3.pdf",
      "mimeType": "application/pdf", "sizeBytes": 1258291,
      "checksumSha256": "9f86d0..." }
    → 201 { "uploadId": "...", "url": "https://s3...", "fields": {...}, "expiresIn": 600 }

 2) PUT/POST the bytes directly to the pre-signed URL (browser or mobile → storage)

 3) POST /v1/documents/upload-sessions/{uploadId}/complete
    → 201 { "id": "...", "version": 1, "scanStatus": "PENDING" }
    The server verifies size and checksum against the object, then queues the virus scan.
    A document with scanStatus != CLEAN is not downloadable and is not counted as supplied.

10.3 SLA Computation
 • The SLA due date is computed from the case type's sla_hours applied to the organisation's business calendar:
   working days, working hours and public holidays. A 24-hour SLA raised at 16:00 on a Friday is due at 11:00 on the
   following Monday, not on Saturday.
 • Time spent in ON_HOLD and AWAITING_INFO accumulates into sla_paused_ms and is excluded from elapsed time.

13.2 Offline Behaviour
The application is online-first with a bounded offline queue. It does not attempt full offline replication — that would
create merge conflicts the business has no rule for.
 • Read cache: the last 50 cases, their tasks and their metadata are stored in SQLite via Drift and shown with an
   explicit "last synchronised" timestamp.
 • Write queue: comments, task completions, approvals and captured documents are queued locally with a client-
   generated UUID used as the idempotency key.
 • On reconnection the queue drains in submission order; each item is retried up to five times with exponential
   backoff.
 • A conflict — the case moved on while the device was offline — surfaces as an explicit resolution card showing
   both states. It is never resolved silently.
 • Approvals older than 24 hours in the queue are cancelled and returned to the user for re-confirmation, because
   the decision context may have changed.
 • Captured images are compressed to at most 2 MB before queueing and are uploaded only over the pre-signed
   URL flow.

 6. Verify the provider signature over the raw request body before parsing the JSON. A body that fails verification is

18.2 Migration Discipline
 • Migrations are forward-only. A mistake is corrected by a new migration, never by editing a merged one.
 • Expand then contract: add the new column, backfill in a job, deploy code that writes both, deploy code that reads
   the new one, and only then drop the old column — in a later release.
 • A migration that rewrites a large table runs as a background job with a progress log, not inside the deploy step.
 • Every migration is tested against a staging copy of production-sized data before it reaches production.
 • Index creation on a live table uses CREATE INDEX CONCURRENTLY.
